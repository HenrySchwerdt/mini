# Wall time against Rust (`claude/perf-16`)

Until now the campaigns counted instructions (callgrind). This one measures time: `bench/walltime.sh` builds every benchmark with mini (C
backend, `minic build -O2`), mini (LLVM API backend, `--opt=O2`) and Rust (`rustc -C opt-level=3 -C codegen-units=1`), pins every run to one core
with `taskset`, does one warm-up run and takes the median of N runs; the binaries run interleaved (C, LLVM, Rust, C, ...) so that drifts of a shared
machine hit all of them. `MINIC_API=<minic-native with the LLVM C API> bench/walltime.sh -n 7` prints the table below.

with a build running next to it: the noise of the machine is of that size; the minimum columns of the script's output are steadier.)

Where wall time is clearly worse than the instruction ratio: json (1.16x instructions, 1.34 to 1.55x time), strbuild (1.02 / 1.20), wordcount
(1.05 / 1.31). graph (2.22 / 2.42) and fannkuch (1.40 / 1.05: better than its instructions) agree or are better.

## Cause: the number of memory hops

`valgrind --tool=cachegrind` (there are no hardware counters here), json with 1 and with 5 repetitions of parse + walk + free, so the marginal
cost of the later repetitions shows: Rust 11.4 M D1 read misses in total for 5 repetitions (2.3 M each after the first), mini 17.9 M (3.8 M each; 2.6 M for
the first). Per function (mini): `walk` 6.0 M of the misses, the teardown (`ArrayList.dispose`, `ref_array_dispose`, `JObj/JArr/JStr.dispose`) about
7 M, the parser almost none (fresh sequential memory). A Rust `Vec<J>` holds its elements inline; the same node in mini is a `JArr` object, an
`ArrayList` object, a `RefArray` and one object per element, so a traversal hops through three to four cache lines where Rust touches one or
two. The instruction count does not show this; the time does. Branch mispredictions (cachegrind `--branch-sim`: mini 47 M against Rust 33 M) add less.

Tried and dropped: **FIFO free lists** (reuse blocks in the order they were freed, which would restore the allocation order of the first repetition):
the blocks come back cold. json 1.07 s to 1.23 s, graph 1.81 s to 2.10 s, binarytrees 1.33 s to 2.44 s user time; reverted.
The LIFO order is what keeps the freshly freed (hot) block for the next allocation.

What would help is fewer hops (storing the `ArrayList` elements inline in the list object for the first few elements, or one allocation for list
object and storage): a change of the stdlib data structure and of every user of `ArrayList.array`, left for its own campaign.

## LLVM backend against the C backend

At least as fast on every benchmark except json and binarytrees (within 5 percent, inside the noise) after one fix; before it, spectralnorm was
1.20x Rust (18.0 G instructions against 12.5 G for C): the LLVM lowering of `for (i in a until b)` used the exact counting loop (distance
arithmetic and a 64-bit induction variable). It now emits the plain loop of the C backend (`add nsw`, test `cur < last`; `IrOp.ADDNSW`, `LLVMBuildNSWAdd` in the API
builder), switched off by `-Xno-plain-loops` like the C form: spectralnorm 1.64 s to 1.31 s, instructions 18.0 G to 17.5 G (the rest is a signed
division by two that clang proves non-negative in the C form and LLVM does not). graph and wordcount are faster with the LLVM backend (1.68 s against 2.00 s;
1.80 s against 2.00 s).
