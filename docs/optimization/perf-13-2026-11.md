# The cost of the object model (`claude/perf-13`)

Same host and method as [perf-12-2026-11.md](perf-12-2026-11.md) (C backend, `-O2`, callgrind instruction totals, an `-O2` runtime).
"Before" is the `claude/perf-12` toolchain.

## Where graph and json spend their instructions

Per function (callgrind), graph (2.23 G) and json (3.82 G):

| part | graph | json |
|---|---:|---:|
| allocation (`mk_alloc_armed` / `_plain` / `_sized`, `mk_ref_array_new`, zeroing) | ~300 M (13%) | ~430 M (11%) |
| release and teardown (`mk_release`, `mk_release_armed`, `ref_array_dispose`, dispose functions) | ~700 M (31%) | ~1000 M (26%) |
| cycle candidates (`cycles_candidate`, `slots_put`) | ~220 M (10%) | small |
| `ArrayList.add` | ~390 M (17%) | ~180 M (5%) |
| the program itself (loops, field reads, type tests) | the rest | the rest |

Reference counting itself is cheap where it is inlined (the `MKH_RETAIN` / `MKH_REL` fast paths); the cost is in what happens at
zero (the dispose chain, the cycle-candidate bookkeeping of armed objects) and in the allocator entry: `mk_alloc_armed` was a call that
checked the collector, loaded the instance size, computed the size class and zeroed through a switch or a `memset` call: about 60 instructions
per object.

## Changes (each with a switch and a test)

* **Inline small-object allocation** (`-Xno-inline-alloc`, `mkh_alloc_inline` in the C prelude, `MkSmallCache` now in minirt.h): a class
  instance of at most 64 bytes takes its block from the thread's small-object cache in generated code (free-list pop, else the bump chunk),
  zeroes it with plain stores (the size is a constant) and writes the header; an empty class, a full chunk or a collector that is not installed yet
  go to the runtime entry, which does the same. Only where the runtime itself uses the small allocator (no `MK_STATS`, `MK_PLAIN_MALLOC`,
  Windows, wasm, AddressSanitizer: the macro `MK_INLINE_ALLOC`); the LLVM backend keeps calling the runtime. Test: compiler/testdata/alloc_inline.kt
  (free-list reuse, zeroed fields in reused blocks, 16 to 72 byte classes, armed and plain, collector, another thread).
* **Reference-array storage** (`mk_alloc_sized_armed`): `mk_ref_array_new` allocates through the small allocator directly (it was
  `mk_alloc_sized` with its allocator and type tests), and `zero_small` stores inline up to 128 bytes instead of calling `memset`.
* **`ArrayList.add`**: the storage and the length are read once on the common path.

## Not done

* Smaller object header (16 bytes: type word, count, flags): the type word could shrink to 32 bits only with a type table, a change of every
  emitter and of the LLVM layout; not attempted.
* Skipping cycle candidates for classes that cannot form a cycle: `Node -> ArrayList -> Node` can, and collections are generic and erased, so
  `ArrayList` itself must stay armed.
* Borrow elision (no count change for borrowed reads) is what `RcOpt` already does; the remaining retains are stores into collections.
* fannkuch `memmove`: the loop idiom is made by the C compiler; the per-function `no_builtin` attribute would also remove the (profitable) calls
  for long copies, and a barrier in the loop body costs more than the call (measured: +6 G); left alone.
