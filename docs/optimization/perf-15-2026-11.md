# Cheaper cycle-candidate bookkeeping (`claude/perf-15`): not worth it

Starting point: `claude/perf-13` (58fa550). The cost, from [perf-14-2026-11.md](perf-14-2026-11.md): every armed object that is released once without
dying becomes a candidate: one entry in the `roots` vector and one entry in the hash table `slots` that finds that entry again when the
object dies while buffered (`slots_put` 78 M, `cycles_candidate` 48 M, `release_buffered` 50 M for the 1 M nodes of graph).

## Variants

* **Index in the header**: the header has 8 bytes (type word, count, flags); the flags word has the bits 19 and 21..31 free, 12 bits, and the
  index needs 21 (`MAX_SLOTS`). Not possible without growing every armed object.
* **Zombies, no hash table** (the design of this campaign, implemented in `cycles.c` / `object.c` and measured): a buffered object that dies runs
  its dispose and keeps its block, colour `DEAD`; the next collection (or a reclaim pass) finds it in the vector and frees the block. `slots`,
  `slots_put`, `slots_take` and the `forget` hook are gone. (This is the design the collector had before commit 929bde7 replaced it
  by the slot index, then by the table.) Because dead blocks are not reused while they wait, the memory they hold must be bounded: a plain
  pass over the vector (`reclaim_zombies`, no marking) frees them once they hold `ZOMBIE_CAP` bytes or half the buffer.
* **A vector with lazy deletion** is the same thing: whatever does not know the index of a dying object cannot remove it, so the block has to
  stay.

## Result: does not pay

* json gains nothing in any variant (its buffered objects are few; its instructions are in allocation and plain release) and its peak RSS
  grows 9 percent for every cap of 4 MiB and above; at 1 MiB it is +3.5 percent but graph is then 6 percent worse.
* graph gains 4.5 percent only when the zombies are not bounded (RSS +15 percent); with a bound the gain shrinks to 3 percent at 16 MiB and
  turns into a loss below that, because every reclaim pass walks the whole buffer (1 M live purple roots).
* The criteria (fewer instructions for graph and json, peak RSS at most +5 percent) cannot be met together, so the runtime is unchanged on this
  branch. The collector's own comment and the history (929bde7) record the same trade: the table costs instructions, the zombies cost memory.

Possible later work: make the reclaim pass incremental (it walks only the entries added since the last pass), which would remove the loss
at small caps; the best case is graph -3 percent and json 0, which is below what the added complexity justifies today.
