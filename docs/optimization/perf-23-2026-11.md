# json and wordcount against Rust: analysis (`claude/perf-23`)

Goal: bring json (about 1.26x Rust wall time) and wordcount (about 1.2x) to Rust level with string / char / StringBuilder / parsing work. Result of the
investigation: **no compiler or runtime change was made**. Every candidate that was found is either already covered by earlier rounds, belongs to the
HashMap / ArrayList internals (the perf-graph task, not touched here) or is too small to justify its risk. The numbers below are what the next round starts from.

All counts are callgrind instructions of the whole program, `-O2`, LLVM backend (text-IR path, same as the API path), symbols kept.

## json (LLVM 3.509 G, C 3.585 G, Rust 3.096 G)

| function (LLVM) | Ir | share | note |
|---|---:|---:|---|
| `Parser.parseValue` | 521 M | 14.9% | 3.7 M calls, about 140 instructions per call (Rust `parse_value`: 335 M) |
| `mk_release` + `mk_release_armed` | 837 M | 23.9% | dropping the five trees; Rust: `_int_free` + `free` + `malloc_consolidate` + unlink about 700 M |
| `Parser.parseString` | 405 M | 11.6% | scan loop about 12 instructions per character (Rust 220 M) |
| `walk` | 388 M | 11.1% | 3.7 M calls of about 107 instructions (Rust: 181 M) |
| `ArrayList.add` / `ArrayList.<new>` | 145 M / 66 M | 6% | collection internals: out of scope here |
| `mk_alloc_sized_armed`, `ref_array_dispose` | 134 M, 126 M | 7.4% | ArrayList storage |
| `mk_string_substring` + `string_alloc8` + `substring` wrapper | 273 M | 7.8% | one Latin-1 string per parsed string |

Rust spends 1.3 G of its 3.1 G in malloc / free (`_int_malloc` 489 M, `_int_free` 249 M, ...); Mini's allocator and release are cheaper than that, the
gap sits in the generated parser / walker code and in the cache / branch behaviour:

cachegrind (branch and cache simulation) LLVM vs Rust: instructions 3.51 G vs 3.10 G, branches 690 M vs 480 M, **mispredicted 46.4 M vs 33.7 M**
(indirect: 9.0 M vs 5.3 M, the `dispose` function pointer called through the type info when a tree is freed), D1 misses 19.3 M vs 16.6 M. Of the roughly
0.2 s wall time difference, about a third is explained by the additional mispredictions, the rest by the 13% more instructions.

### What was looked at and why nothing was changed

- **Latin-1 / UTF-16 dispatch per character.** Every string scan (`parseString`, `skipWs`, the digit loop, `walk`, `hash`) tests the `MK_FLAG_LATIN1` bit
  of the flags word per character (`test [s+0xe],0x10` / `test edx,0x100000`) - 3 of the 12 instructions of the scan loop. The flag cannot be hoisted by
  loop-invariant code motion alone and the loop is not unswitched at `-O2` (non-trivial unswitching is off). Experiment: `clang -O2 -mllvm -enable-nontrivial-unswitch`
  on the emitted IR: 3.509 G -> 3.495 G (-0.4%), identical size, so the pass does not even find these loops. A hand-made versioning of the scan loops in the
  lowering would save at most 3% of json and is a bigger change than the gain justifies.
- **`StringBuilder.append(Char)`** (wordcount `generate`): the inline sequence is 14 instructions (inner null test, length, capacity, `wide` flag, data pointer, store,
  length store) against about 6 in Rust's `String::push`; `generate` is 281 M vs 233 M for 2 M words (+21%). Merging the capacity and the wide test needs a change of the
  StringBuilder layout shared with the C prelude and the wasm runtime: not done.
- **`substring`**: three layers (stdlib wrapper range test, `mk_string_substring` range test again, `string_alloc8`); the second test is cheap and the allocation is
  the small-cache path. Nothing measurable to gain.
- **Sealed-class `when` in `walk`**: sequential `cmp` against the four type-info addresses, a checked cast of every element read from `ArrayList<J>` (6 instructions) and
  seven pushes / pops per call. These are consequences of the memory model (heap-pollution safe casts), not of the string handling.

## wordcount (LLVM 8.249 G, C 8.564 G, Rust 9.507 G)

Mini executes **fewer** instructions than Rust here (0.87x). Profile (LLVM): `mkh_user_main` 4.645 G (generation of the 20 M words 2.8 G, the counting loop 1.8 G), `HashMap.findNodeRange`
1.210 G, `mk_string_hash_range` 1.073 G, `mk_string_equals_range` 1.042 G (the counting loop already looks up `counts[text.substring(pos, e)]` by range, without
materializing the substring: `opt/SubstrKey.kt`). The remaining wall-time gap (1.595 s vs 1.317 s in perf-21) is therefore not an instruction problem: it is the memory behaviour of the
boxed `Int` values and the node objects of the HashMap (cache misses on a 70 MB text and 8 M-entry-class table). That is exactly the area of the perf-graph work (HashMap
internals, boxing of Int values) and was left alone as requested.

## Benchmarks before / after

No source of the compiler, runtime or stdlib changed in this round, so every instruction count and size equals the table of `perf-22-2026-11.md`
(HEAD of `claude/perf-22`): json 3.509 G, wordcount 8.249 G, fannkuch 11.838 G, spectralnorm 12.503 G, nbody 8.700 G, mandelbrot 6.729 G, strbuild 5.640 G, graph 1.951 G,
binarytrees 10.766 G, concurrent 3.546 G; sizes unchanged.

## Where the next gain is

1. Loop versioning of string scan loops on the Latin-1 flag (about 3% of json, similar for parsing code in general).
2. A cheaper `StringBuilder.append(Char)` fast path (needs a layout change across C prelude, LLVM lowering and wasm).
3. Fewer mispredicted indirect calls when freeing trees (devirtualize `dispose` for the closed set of a sealed hierarchy).
4. wordcount: the HashMap work of perf-graph.
