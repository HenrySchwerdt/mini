# fannkuch and spectralnorm under LLVM: typed array GEPs and the loop test in the header (`claude/perf-22`)

Under the LLVM backend fannkuch and spectralnorm needed 26% / 40% more instructions than the C backend (callgrind, `-O2`, whole program):

| | C | LLVM (before) |
|---|---:|---:|
| fannkuch | 13.687 G | 17.206 G |
| spectralnorm | 12.503 G | 17.502 G |

## Causes (IR / asm of both builds)

1. **Array elements were addressed by byte offset.** The inline array accessors computed `gep inbounds i8, arr, sext(idx) * size + header`. The
   optimizer cannot tell that this byte offset does not wrap, so scalar evolution sees no affine access `elems[idx]`; the flip loop of fannkuch was not
   unrolled and the inner loops did not get the strength reduction that clang gives the C output (`MK_ARRAY_ELEMS(T, a)[i]`).
2. **The counting loop tested at the bottom.** `for (i in a until b)` was lowered as a guard in front of the loop and the test at its end. The passes that
   run before the loop rotation (CorrelatedValuePropagation, InstCombine) then do not know `0 <= i < last` inside the body, so
   `(i + j) * (i + j + 1) / 2` in spectralnorm kept the signed-division sequence (add sign bit, sar) instead of a plain shift.

Not needed: the two changes already bring both benchmarks to the C backend's count, so hoisting of bounds checks / length reloads, vectorization and `nsw`/`nuw`
(the counting loops already carry `add nsw`) were not pursued further. No fast-math flags are used.

## Changes

- `IrBuilder.gepElem(base, elemType, index)` (text and API builders): `getelementptr inbounds <elem>, ptr base, i64 index`. `arrayAccess` and the reference array
  accessors address `elems[idx]` with it (the base is `arr + header`). Switch: **`-Xno-typed-array-gep`** (`CEmitter.typedArrayGep`).
- `plainForRange` (Lowering.kt) puts the test `cur < last` in the loop header (`frhdr`), the body is dominated by it, the advance branches back to the header.
  Switch: **`-Xno-for-header-test`** (`CEmitter.forHeaderTest`).
- Tests: `LlvmEmitterTest.arrayElementsAreTypedInboundsGeps`, `plainForLoopTestsInTheHeaderAndSwitchRestoresTheGuard` (default shape and shape with the switch).
  The existing e2e corpora (fannkuch-like array code, index failures, `until` loops incl. empty and `Int.MAX_VALUE` bounds) run through the llvm suites.

## Measurement

callgrind instructions (billions, whole program), binaries from `compiler/bootstrap.sh --backend=llvm-api` (API path) and the text-IR path
(`--emit-ll` + `clang -O2`; both give the same counts). "before" = `-Xno-for-header-test -Xno-typed-array-gep` (the code of perf-21), "after" = default; C is the C backend.

No benchmark got worse. Executable size (stripped, `--gc-sections`, bytes) is identical before and after for every benchmark
(fannkuch 39 608, spectralnorm 39 608, nbody 35 368, mandelbrot 31 272, strbuild 43 592, json 76 512, graph 68 320, wordcount 84 704, binarytrees 43 704,
concurrent 133 952, hello 14 824).

Wall time (median of 5, pinned to one core, the machine was shared at a load average of about 20, so differences below about 10% are noise;
C / LLVM before / LLVM after, seconds): fannkuch 3.58 / 3.73 / 3.36, spectralnorm 1.80 / 1.77 / 1.83 (second run 2.18 / 2.22 / 2.23),
nbody 1.40 / 1.38 / 1.35, mandelbrot 1.62 / 1.63 / 1.64, strbuild 0.72 / 0.62 / 0.60, json 1.83 / 1.90 / 1.92, graph 2.56 / 2.52 / 2.45,
wordcount 2.39 / 2.33 / 2.25, binarytrees 2.26 / 2.06 / 2.06, concurrent 1.22 / 1.13-1.23 / 1.19-1.32. The instruction counts are the reliable measure here.
