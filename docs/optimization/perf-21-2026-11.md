# json under LLVM: inline allocation and noreturn string failure paths (`claude/perf-21`)

json ran at 1.46x Rust under the LLVM backend and 1.25x under C. callgrind of both builds (same sources, symbols kept, instructions):

| | C | LLVM (before) |
|---|---:|---:|
| json total | 3.585 G | 3.991 G (+11%) |

## Where the difference was

1. **No inline allocation in the LLVM backend** (about 300 M). The C prelude's `mkh_alloc_inline` takes a small object's block from the thread's small cache
   (free list, else bump chunk) with a handful of instructions and zeroes it with plain stores. The LLVM constructor wrappers (`<ctor>_new`) called
   `mk_alloc_armed` / `mk_alloc_plain` (`mk_alloc_armed` 208 M + `mk_alloc_plain` 98 M instructions in the profile).
2. **The failing paths of `String.length` / `String[i]` joined the fast path again** (about 100 M in `Parser.parseString`, `parseValue`). The slow path of the
   inline `charAt` called `mk_string_char_at` and merged back with a value; since that call may write memory, LLVM reloaded `this.s` and `this.pos` from
   memory after the merge on every iteration of the scanning loop (`while (s[pos] != '"')`) instead of keeping them in registers, and did not combine the two
   `s[pos]` loads. The C prelude's failure paths are `noreturn` (`mkh_fail_str_char_at`: the runtime function panics, then `mk_panic`).

## Changes

- **`mkh_alloc_c<1..4><a|p>(ti)`** (compiler/backend/src/llvm/Lowering.kt, `emitAllocHelpers`): always-inline helpers, one per size class and per armed / plain, the same sequence as
  `mkh_alloc_inline`: for an armed class `mk_cycles_ready` is tested, the class's free list is popped, else the bump chunk is checked for alignment and room, the
  block is zeroed, header (type, refcount 1, flags with class and ARMED) written, the thread's `cycles_bytes` share advanced; anything else takes
  `mk_alloc_armed` / `mk_alloc_plain`. The constructor wrappers of classes of at most 64 bytes call them. `mk_small_cache` is reached as an
  `external thread_local(initialexec)` global (new `IrBuilder.externGlobal`, text and API builders). Only on 64-bit hosts without the JIT's pending-slot accessor (not wasm, not Windows,
  not with `-DMK_STATS` / `-Xno-inline-alloc`).
  The struct offsets are asserted in runtime/src/alloc_small.c (`_Static_assert` on `count`, `bump`, `end`, `cycles_bytes`). A runtime built without the small allocator (ASan,
  plain malloc) now defines an empty `mk_small_cache`, so the generated code still links and always takes the runtime.
- **`noreturn` string failure paths**: the null / out-of-range branches of the inline `String.length` and `String[i]` end in `unreachable` after the runtime call.

## Result

| benchmark (LLVM backend, callgrind instructions) | before | after |

| fannkuch, nbody, spectralnorm, mandelbrot | identical | identical |

json: LLVM is now level with C (3.509 G vs 3.585 G instructions, 1.224 s vs 1.233 s). No LLVM benchmark got worse.

## graph (C, +1.1% left from perf-20)

No further cause found: the cold bounds-failure code, the counter and the runtime were checked in perf-20; the remaining 1% is a different register allocation / layout of
`mkh_user_main`. It stays documented.
