# Precompiled libraries (`.mlib`)

A `.mlib` is a library compiled once: the **API stubs** of its sources and its **full, unpruned MIR** in one text file. A program
that uses it parses only the stubs (declarations, no code), lowers its own code, links the library MIR into its own at the MIR
level, prunes from `main` and goes on to the C emitter, the LLVM emitter or the JIT as before. The standard library is one
(`lib/stdlib.mlib`, built by `scripts/build-mini.sh` and shipped in every release), and so is every Mini package that is not the
program being built.

Why this shape: the MIR is target independent (the same file feeds the C backend, the LLVM backend, the ORC JIT and the wasm build),
and the stubs keep the real file names, lines and columns, so diagnostics, hover texts and debuggers point at the library source.

## Using it

```sh
minic-native --emit-mlib stdlib.mlib --name stdlib --compiler-id 0.6.0 --no-memory-check $(find stdlib -name '*.kt' | sort)
minic-native --emit-mlib geometry.mlib --name geometry --lib-version 1.2.0 --lib stdlib.mlib src/*.kt
minic-native -o app.c app.kt --lib stdlib.mlib --lib geometry.mlib       # --lib is repeatable
minic-native --check app.kt --lib stdlib.mlib                              # stubs are enough to check
```

* `--emit-mlib <out>` compiles all given files into a library (they are library code: every declaration is kept, nothing is
  pruned). `--name`, `--lib-version`, `--compiler-id` fill the header. The memory checker runs over the library sources as for a
  program (`--no-memory-check` skips it; the standard library, which is not Strict-clean, is built that way).
* `--lib <x.mlib>` (repeatable) adds a library to a compilation. Libraries a library was built against (its `dep` lines) must be given
  too. `--stdlib <files>` (the source mode of the bootstrap and of the tests) keeps working and can be combined with `--lib`.
* `minic` and `mini` use `lib/stdlib.mlib` of the installation by default; `MINIC_STDLIB=source` / `MINI_STDLIB=source` switches back
  to compiling the sources with the program.
* `mini build` builds every dependency package (path and git dependencies alike) to `build/mlib/<name>-<fingerprint>.mlib`, once;
  the fingerprint covers the sources, the libraries it needs and the toolchain, so a library is rebuilt only when one of them changes.
  `mini package` writes the distributable `build/package/<name>-<version>.mlib`.

## Format (version 1)

One text file; the sections are length-prefixed (lengths in characters), so no escaping is needed.

```text
mini-mlib 1                      magic and format version
mir-format 2                     version of the MIR text (MirWriter)
compiler <id>                    identity of the compiler that built it (the toolchain version)
name <name>
version <version>
tag <tag>                        L<8 hex>_ : makes generated names unique among linked modules
hash <16 hex>                    FNV-1a over name, version, compiler, format, deps, stubs, failures and MIR
dep <name> <hash>                zero or more: libraries this one was built against
fail <cName> <message>           zero or more: functions the backend cannot lower (see below)
stub <length> <path>             one per source file: the stub text follows, then a newline
mir <length>                     the MIR text follows, then a newline
end
```

**Stubs.** The original source file with the bodies the consumer does not need blanked out (`StubWriter`, `StubRules` in
`compiler/frontend/src/Stubs.kt`): bodies of functions, accessors, constructors and `init` blocks, and initializers of properties. What is
kept: `inline` function bodies (the consumer expands them at every call site), expression bodies without a declared return type
(the type is inferred from them), `const` and untyped initializers. A blanked region keeps its newlines and the text after it keeps
its column. The analysis does not check what a stub does not keep, and the IR builder does not build it.

**MIR.** The module of `MirWriter` (`compiler/backend/src/MirSerial.kt`): all classes, all functions, C externs, `CInclude` and `CLink`.

**Generated names.** Closure classes, lifted local functions and `staticCFunction` wrappers carry the library `tag`, so two libraries
never define the same name. Overloads that differ only in a pointer type get a suffix from their parameter types (not from declaration
order), so a library and a program compiled against its stubs agree on every name. The same helper generated by several modules (function
interfaces, bridges, reference cells) is identical and kept once.

**Unsupported constructs.** Source-level pruning let the standard library carry functions the backend cannot lower (`average` over
`Iterable<Number>`, bridges for `Iterator<Byte>`), because nothing reachable used them. A library lowers every function, so such a
function is recorded as a `fail` line and replaced by a stub that panics; the link reports the recorded error, as a compile error, only
when a program actually reaches the function.

## Linking

`lowerToMirWithLibs` (`compiler/lower/src/Mlib.kt`): the program and the stubs of all libraries go through the frontend and `Ast2Ir`
(stub files are `IrFile.isLib`: their functions have no bodies, `Ir2Mir` names them but emits nothing for them), `Ir2Mir` produces the
program MIR, `MirLink.link` merges library MIRs (dependencies first, then the program; the first definition of a C name wins) and
`MirLink.prune` removes everything `main` cannot reach: functions through calls and addresses, classes through any mention of their type,
a reachable class keeping its vtable and itable functions. A program without `main` keeps all its own functions.

## Errors

| Situation | Message (exit status 1) |
|---|---|
| not an mlib | `x.mlib: not a Mini library (no 'mini-mlib' header) ...` |
| other format / MIR version | `library format version N, but this compiler reads version 1; rebuild the library with this toolchain` |
| built by another compiler | `library 'x' was built by compiler 'a', this one is 'b'; rebuild the library` |
| edited or damaged | `content hash mismatch (header says ..., content is ...)`; truncated files say so |
| missing dependency | `library 'a' needs library 'b' (hash ...), which was not given (--lib <path to b.mlib>)` |
| wrong dependency | `library 'a' was built against 'b' with hash X, but the given 'b' has hash Y` |

## Browser toolchain

The browser build uses the same format. `scripts/build-wasm-toolchain.sh` places `stdlib.mlib` and a `libs.json` containing the
preinstalled libraries' metadata plus separate `.mlib` assets. The standard library loads with the checker; each preinstalled library
loads only when a program imports one of its packages. The worker includes recorded dependencies and passes selected files with
repeatable `--lib` flags. This lets the compiler parse library API stubs
and link MIR instead of parsing and lowering each library's full source on every edit. Browser manifests with the older
`stdlib.json` and source-based `libs.json` remain supported by the worker.

## Consumers other than the C backend

The MIR text is the same for every target. The LLVM backend, the ORC JIT (`--backend=llvm-api --run`) and the wasm build take the module
`lowerToMirWithLibs` returns; nothing in the format is C specific. A package registry stores the `.mlib` files `mini package` writes; the header carries name, version, compiler and
the hashes of the libraries it needs.

## Limits and follow-ups

* An `inline` function that touches `private` or `internal` library members works (the consumer calls them by their C names, which are
  in the library MIR); a local class declared inside an inline function body is not supported across libraries.
* The whole MIR text is parsed on every program build; a per-function index (parse only the reachable bodies) and a per-target object cache
  (`~/.mini/cache/<hash>/`) are the next steps for faster builds and for the JIT/REPL.
* Top-level properties of a library are initialised lazily, on first access (file facades are objects created on first use); a program's own
  top-level initialisers still run before `main`.
